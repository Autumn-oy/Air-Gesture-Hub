```
app/build/outputs/apk/debug/app-debug.apk
```

把它传到手机（数据线／微信文件传输／adb），在手机上点击安装。

```bat
adb install -r app\build\outputs\apk\debug\app-debug.apk
```

### 方式 B：自己编译

**用 Android Studio（推荐给要改代码的人）**：直接 `File → Open` 选中本 `android` 目录，
等 Gradle Sync 完成后点 Run 即可。`local.properties` 里的 `sdk.dir` 是这台机器上的
工具链路径，Android Studio 通常会自己覆盖成你的 SDK 路径。

**用命令行**（本工程实测可用的组合）：

| 组件 | 版本 |
|---|---|
| JDK | 17（Temurin 17.0.20） |
| Gradle | 8.13 |
| Android Gradle Plugin | 8.13.2 |
| Kotlin | 2.4.20 |
| compileSdk / targetSdk | 36 |
| minSdk | 29（Android 10） |
| MediaPipe Tasks Vision | 0.10.35 |
| CameraX | 1.6.2 |

⚠️ **必须在纯 ASCII 路径下用命令行编译。** 本工程所在的 `...\隔空手势\android` 含中文，
实测会踩两个坑：

1. AGP 直接拒绝：`Your project path contains non-ASCII characters`（`b.android.com/95744`）。
   `gradle.properties` 里的 `android.overridePathCheck=true` 能绕过它，**但这只解决了第一个坑**；
2. **单元测试仍然失败**：测试 worker 的 classpath 要经过文本文件传递，非 ASCII 路径解析出错，
   报 `ClassNotFoundException: ...SweepDetectorVectorTest`（类其实编译出来了）。

所以带了一个镜像构建脚本，它把工程同步到 `E:\airgesture`（ASCII）再编译，最后把 APK 拷回来：

```bat
:: 编译（APK 会拷回 android\app\build\outputs\apk\debug\）
powershell -ExecutionPolicy Bypass -File android\tools\build.ps1

:: 编译 + 跑单元测试
powershell -ExecutionPolicy Bypass -File android\tools\build.ps1 -RunTests
```

脚本里的工具链路径是这台机器的，换机器请改 `build.ps1` 里的 `$root`，
或者直接用 Android Studio（Android Studio 自己处理路径，不受上面两个坑影响）。

> Android Studio 打开本目录时，`local.properties` 里的 `sdk.dir` 会被自动覆盖成你的 SDK 路径。

## 二、第一次使用（三步）

1. **给相机权限**：打开 App → 点"请求相机权限"。
2. **开启无障碍服务**：点"打开无障碍设置" → 在列表里找到「隔空扫动」 → 打开。
   *这一步没法自动完成，是 Android 的硬性要求。*
3. **做一次标定**（强烈建议）：回到 App → 点"开始标定" → 按提示依次做
   **向上／向下／向左／向右各扫 5 次**。标定会自动算出触发阈值和支架角度补偿。

标定完就能用了。屏幕上会有一个小状态条显示当前状态，不想要可以在设置里关掉。

## 三、怎么用

### 3.1 动作规格（已按渲染图确认）

**动作本质是"手腕扫动"**：四指并拢，手指像雨刷一样从一边扫到另一边。
关键结论：**四指指尖质心的移动方向 = 你要的方向**，判定器用的就是这个量。

| 方向 | 起始姿势（1） | 结束姿势（2） | 质心往哪走 | 注入 |
|---|---|---|---|---|
| **向上** | 手指朝**下**（手接近水平） | 手指朝**上**（手竖起） | ↑ | `ACTION_SCROLL_FORWARD`（内容往上走） |
| **向下** | 手指朝**上** | 手指朝**下** | ↓ | `ACTION_SCROLL_BACKWARD` |
| **向右** | 手指朝**左** | 手指朝**右** | → | 合成滑动（向右） |
| **向左** | 手指朝**右** | 手指朝**左** | ← | 合成滑动（向左） |
| 手指张开 | — | — | — | **故意不判定**（压误触发最有效的一道门控） |
| **不足四根手指** | — | — | — | **故意不锁定**（见 3.3：一根手指不能触发） |
| 手离开画面 | — | — | — | 回到待机，不会让屏幕乱滚 |

**每一轮的完整流程（用户确认的规格）**：

```
动作1  四指并拢伸出、摆好起始姿势
       ↓  手停稳 250ms **且四指都伸出来** -> 姿势锁定
       弹窗「请滑动」          <- 这是"动作1做完、该做动作2了"的出发信号，每一轮都出现
       ↓
动作2  扫动（姿势1 → 姿势2）  -> 位移越过阈值的那一帧判定方向 -> 注入一次滑动
       ↓  ★ 冷静期从**这一瞬间**开始计时（不是等滑动播完）
冷静期（默认 1500ms）         -> 扫动的后半截 + 顶点停顿 + 收手归位全被忘掉
       ↓
新一轮（状态回 SETTLE：同样要"四指伸出 + 停稳"才再解锁）
```

**方向在什么时候判定**：动作2 一开始、位移越过阈值时就判定了（你的扫动幅度约 0.45 屏高，
阈值 0.10，所以大约在动作2 进行了 1/5 时），**不等你把姿势完全摆到位**——这样延迟最低。
如果你更想要"姿势摆完再滑"，可以改成等动作结束，代价是多约 100~200ms 延迟。

**冷静期的计时起点（v0.15.1 明确）**：是**判定触发的那一帧**，不是"合成滑动播放完"之后。
这一帧之后发生的所有位移（扫动的后半截、顶点停顿、收手归位）都落在窗口里，
一次都不会被累积。真机上可以在悬浮窗第二行看到 `冷静 1234ms` 从 1500 往下掉。

**上下扫的位移天然比左右扫小**：上下扫时手指有一段是指向镜头的，投影被压缩。
所以标定时按方向分别量位移、**取最小的那个**来定阈值，否则上下会明显更难触发。

> v0.10.0 起去掉了 v0.7~v0.9 那个"归位判定"状态（曾要求手回到出发点并停稳才重新武装）。
> 那是**方向还判不准的阶段**用来保命的；现在方向问题已在坐标系层面解决，
> 加上轴向容差，"靠冷静期把上一轮整段忘掉"就够了。
> 代价与确切边界见 7.2。

**操作提示**（可在设置里关）：进入"姿势已锁定、可以做动作2"状态时出现 **「请滑动」**，
灰色圆角矩形、低透明度，约 0.9 秒后自动消失。

> v0.16.0 曾把它改成"常驻不消失"，用户试用后否掉了（v0.16.1 改回）—— 还是一闪即隐的干净。
> 用不可触摸的悬浮条实现（不是 Toast —— Toast 会排队，连扫时会滞后好几秒）。

### 3.2 合成滑动幅度 ≠ 目标应用滚动的距离（很重要）

"注入一次滑动"和"目标应用滚了多远"之间**没有固定的换算**——是**目标应用自己**按它自己的
阈值和惯性去解释这次滑动。所以"我设的幅度和目标应用滚动的幅度对不齐"是必然的，要点是：

| 目标行为 | 决定它的量 | 说明 |
|---|---|---|
| **桌面翻页 / 相册翻屏（分页视图）** | 各家的规则都不一样（"拖过半屏"、"靠速度甩"、或两者都有） | **不接管**（见 3.4）：桌面固定不响应 |
| 列表滚动 | 拖动距离（拖多少滚多少） | 幅度 0.30 |
| 信息流（抖音/微博，自绘界面） | 拖动距离；速度大会变成惯性连滚 | 幅度 0.30 |
| 长文连续滚动 | 距离越大滚得越多 | 幅度 0.30 |

### `ACTION_SCROLL` 已废除（v0.16.0）

v0.15.2 起默认不再使用，**v0.16.0 把这条通道的代码整体删掉了**。理由（你实测的体感是对的）：

| | **合成滑动（唯一通道）** | ~~ACTION_SCROLL~~（已删） |
|---|---|---|
| 做了什么 | 注入一串**真实触摸事件**，等于一根看不见的手指在屏幕上滑 | 不产生触摸，直接让滚动控件**自己滚**（= TalkBack 的双指滑动） |
| 滚多远由谁定 | 你设的**幅度**（拖多少滚多少），松手带惯性 | **控件自己**决定（通常一屏/一页/固定像素） |
| 手感 | 目标应用的跟手动画、惯性、回弹照常跑 → **顺滑** | 一次性"跳"过去，没有跟手过程 → **一卡一卡** |
| 可靠性 | 通用（真实手指能滑的地方它就能滑） | 只在实现了该动作的控件上有效；自绘界面可能无效，或滚到**错的节点**（抖音那条顶部导航就是它） |

副作用：当年为了让它别滚错节点，还养着一套"遍历整棵无障碍树、找面积最大的可滚动节点"
的逻辑 —— 一并删了，少一处每帧/每次注入的节点遍历。

### 3.3 "四根手指"闸门（v0.15.1 修的就是这个）

**现象（你实测报的）**：只伸一根手指也能触发滑动。

**根因**：原来的门控只有"并拢度"（`together_ratio`），它量的是**四个指尖靠得近不近**，
**完全不问那四根手指有没有真的伸出来**。而 MediaPipe 即使你只伸一根手指，也照样输出
21 个关键点 —— 其余手指是**猜**出来的，通常瘫在掌心附近。于是"单指"的四个指尖依然集中，
并拢度照样 0.8~1.1 过关，闸门被骗过去。这是并拢度这个判据本身的**信息缺口**，只能加新判据。

> ★ v0.16.0 定稿：闸门要求 **≥3 根**，而并拢度上限设成 **2.0**（= 不再用并拢度筛人，
> 因为它对"手指有没有伸出来"这件事没有信息量，真正管用的是手指根数）。

**修法**：移植 Windows 版（`gesture_mouse/gestures.py` 的 `finger_state()`，真实手部数据标定过）
的单指伸展判定，逐根手指看**三个互相独立的证据**：

| 证据 | 伸直 | 蜷曲 | 阈值 |
|---|---|---|---|
| PIP 关节内角（最主要） | ≈175° | ≈68° | ≥135° |
| DIP 关节内角 | ≈168° | 小 | ≥115° |
| 指尖到手腕 / 近端指节到手腕 | ≈1.4 | ≈0.6 | >1.1 |

四根手指（食指/中指/无名指/小指，**拇指不参与**）里伸出的根数 **< 3** 就不锁定姿势：
不会弹「请滑动」，扫动也不会累积位移 → **一根/两根手指怎么扫都不触发**。

> **默认要求是 3 根**（v0.15.2 按用户要求放宽）：要求四根全伸直对少数手型偏严
> （某一根天生伸不太直、或快扫时小指跟不上），而"单指/双指必须挡住"才是这道闸门
> 真正要解决的问题。想更严就在设置里勾上「要求四根手指全伸直」。
> 实测读数（悬浮窗 `手指 x/4`）里 3/4 与 4/4 都算过。

**闸门放在"锁定那一刻"判，而不是扫动过程中逐帧判** —— 这一点很关键：

```
动作1（摆姿势，手是静止的）  -> 此刻判手指根数，关键点干净、判得准  <- 闸门在这里
动作2（扫动）                -> 只量方向，不管手指
```

如果放到动作2 里逐帧判，快速扫动时手指关键点会瞬时漂移（还有运动模糊），
锚点被反复重置 —— 表现出来就是"怎么扫都不触发"。这条已经写成回归测试
（`finger_curl_mid_sweep_still_triggers`：锁定后扫动中手指弯成 2/4 也必须触发）。

**真机上怎么看**：悬浮窗第二行 `手指 3/4`；不达标时显示 `2/4(无名指曲,小指曲)` 这种明细。
「复制诊断信息到剪贴板」里带每一根的 `pip/dip/reach` 原始数值，判不准时发我就能调阈值。

> 为什么不用 MediaPipe 的"手势识别"结果：那要额外加载 gesture recognizer 模型（APK 更大、
> 多一层延迟），而这里只要"四根手指有没有伸出来"这一个布尔量，用已有的 21 点自己算更省更稳。

### 3.4 桌面（启动器）不响应 —— v0.15.0 的取舍

**背景**：v0.14.1 为了"桌面翻页只翻一页"做了一套两段式减速手势（快拖过半屏 + 360ms 慢速收尾
把松手速度压到 fling 阈值以下）。它在本机算得通，但代价是：

- 要**赌** ROM 的 fling 阈值和 `willContinue` 续接触点（有些 ROM 续接处会提前抬手）；
- 会把幅度滑块悄悄顶到"至少 0.58 屏"——用户设 0.30 却怎么都滑不动；
- 上下方向也得跟着过半屏，把信息流的滚动手感一起改掉了。

**所以 v0.15.0 把这一整套删掉了**，改成更简单的规则：

> **前台是桌面时，一次滑动都不注入。** 桌面不在服务范围内。

| 项 | 行为（v0.15.2） |
|---|---|
| 判定方式 | 比较"活跃窗口的包名"和"默认桌面包名"（`CATEGORY_HOME` + `resolveActivity`，**不硬编码** `com.miui.home` 这类）；桌面包名**只解析一次并缓存** |
| 开销 | 每次**手势**跑一次（一分钟几次），不是每帧：一次 `rootInActiveWindow` + 一次缓存比较。**不遍历窗口列表**、不弹提示、不加诊断字段、没有开关 |
| 被跳过时 | 悬浮窗那行结果里写 `桌面·跳过`（复用已有字段，不额外做一层报告） |
| 取不到包名时 | **放行**（宁可手势照常工作，也不要因为读不到包名整个失效） |
| 想改回桌面也生效 | 没有开关 —— 要改就删掉 `SwipeInjector.perform()` 开头那两行 |
| 合成滑动 | **单段匀速**：设多少幅度就滑多少像素，松手带惯性 |

**代价（诚实说明）**：桌面左右扫不会有任何反应。如果你要的是"在桌面上翻页"，这一版**不支持** ——
请在桌面用手指滑动。那套两段式做法（快拖过半屏 + 360ms 慢速收尾）本节的背景里记了原理，
`SwipeInjector` 里已经删除；真要恢复的话按这段描述重建即可。

**不用做手势就能试参数**：~~设置页有「五、滑动测试」~~ —— v0.16.0 已删除（参数定稿了）。

### 3.5 出问题时怎么办（v0.16.0 起没有滑块了）

参数已定稿并内置，页面上的滑块、滑动测试、标定向导、诊断信息**全部删掉了**。
所以现在的排查顺序是"先看悬浮窗，再改常量重编"：

| 现象 | 怎么办 |
|---|---|
| 桌面上扫动完全没反应 | **固定行为**（见 3.4）：桌面不接管，没有开关 |
| **一根/两根手指也能触发** | 看悬浮窗 `手指 x/4`；不够 3 根就不会锁定。若读数明显偏高，说明手型被判成"伸"了，要调 `HandFeatures.ExtendParams` |
| 扫了没反应 | 看悬浮窗：`有手` 吗？状态是不是卡在 `SETTLE`（= 没锁定，多半是指伸不够或手在动）？`位移` 有没有涨过 0.14？ |
| 太灵敏、老是误触发 | 调大 `DEFAULT_ENTER_THR`（`Prefs.kt`）或调大 `DEFAULT_COOLDOWN_MS` |
| 方向整体转了一个直角 | 改 `DEFAULT_ANGLE_OFFSET`（`Prefs.kt`） |
| 只有上下反了 | `Prefs.invertVertical` 默认改 true，或改 `applyOrientation` |
| 只有左右反了 | 改 `Prefs.mirrorX` 默认值 |
| 滚得太少 / 太多 | 改 `DEFAULT_SWIPE_FRAC_V` / `H` |
| 换了手机后屏幕尺寸不同 | 幅度是**比例**，不用改；只有"最小滑动距离 48px"下限在小屏上可能顶到 0.01~0.02 屏 |
| 完全查不出来 | 悬浮窗那几行（帧/回调/见手/手指/冷静期）就是全部诊断信息；把它截图发我 |

**只判定上下左右四个正方向**：斜着扫（方向角偏离正轴超过 ±30°）**不判定**，

### 为什么判定逻辑要写两遍

判定逻辑先在 Python 里实现（`probe/detector_ref.py`）并用 **29 个单元测试**把边界情况钉死，
再由 `probe/make_sweep_vectors.py` 导出 **31 个测试向量**；Kotlin 侧回放**同一批输入**并比对
触发序列（`SweepDetectorVectorTest`）。

手指伸展那一块同理，但参考实现直接复用 Windows 版已经用真实手部数据标定过的
`gesture_mouse/gestures.py:finger_state()`：`probe/make_finger_vectors.py` 造一批合成手
（四指伸直/握拳/单指/两指/三指/整体转 90°/带深度梯度/张开），导出 **11 个向量**，
Kotlin 侧 `HandFeaturesTest` 比对"伸/曲"判定与 PIP/DIP 内角、reach 比值。

这样做的原因很实际：**手机上的手势没法自动测**，但"移植有没有走样"可以自动发现。
和 Windows 版"状态机脱离硬件可测"是同一个套路。

重新生成向量：

```bat
:: 在项目根目录（隔空手势）下
.venv\Scripts\python.exe -m probe.make_sweep_vectors
.venv\Scripts\python.exe -m probe.make_finger_vectors
```

> 生成器把向量按"帧数预算"拆成几个 `partN()` 函数再拼起来 —— 全部塞进一个
> `val all = listOf(...)` 会形成超大的 `<clinit>`，撞上 JVM 单方法 64KB 字节码上限
> （`Method too large: SweepVectors.<clinit>`）。

## 五、已知边界（诚实说明）

1. **锁屏、密码、支付等安全界面收不到手势** —— 系统限制，无法绕过。
2. **必须把手机放稳**（支架最好）。手持时相机自己也在动，"手在动"和"手机在动"分不开。
3. **国产 ROM 可能杀后台**：如果隔一阵就失效，去系统设置里给本应用加后台白名单、允许自启。
4. **无障碍权限需要手动开启**，而且系统重启/应用被强杀后可能需要重新确认。
5. **误触发是这个方案的固有难点**："手往上一扫"和"随手拿起杯子"在图像上是同一类运动。
   目前靠**四道防线**压制：四指都伸出（新）＋ 四指并拢门控 + 位移阈值 + 冷静期。误触发率仍偏高时
   可以再加"张开手掌激活"这道门（代码里预留了口子，尚未实现）。
6. **功耗**：相机 + 推理常开约 1.5~3 W。未激活时目前没有降频（TODO，见下）。

## 七、排错：识别不出来怎么办

### 7.1 v0.1 的 bug（已修，就是它导致"相机在跑但完全没反应"）

**根因**：`MediaImageBuilder` **不拷贝像素**。它的源码只有一行：

```java
public MPImage build() {
    return new MPImage(new MediaImageContainer(mediaImage), timestamp, w, h);
}
```

注释也写明了：*"Once `android.media.Image` is passed in, to keep data integrity you
shouldn't modify content in it."*

而 v0.1 在 `detectAsync` 之后立刻 `proxy.close()`（这是照抄官方示例的写法）。
MediaPipe 是**异步流水线**，等它真正去读像素时那块 `Image` 早就失效了 ——
于是推理永远拿不到有效图像，表现就是**相机指示灯亮着，但永远显示"无手"**。

**修法**（v0.2）：默认走 **RGBA 通道** —— CameraX 直接输出 `RGBA_8888`，
在分析线程里**同步拷贝**进我们自己持有的 Bitmap，再交给 MediaPipe。
Bitmap 由我们持有且不会被回收，所以无论 MediaPipe 什么时候读都是有效数据。
旧的零拷贝通道保留为设置项，可在 App 里一键切换。

### 7.2 手"归位"被当成反向扫动 —— 以及 v0.10.0 的最终解法与代价

**现象（v0.2 时报的）**：手向上扫 → 屏幕往上滑（对），但**把手放回原位的动作又被识别成"向下扫"**。

**演进过程**（值得记下来，因为绕了一圈）：

| 版本 | 做法 | 结果 |
|---|---|---|
| v0.2 | 靠 400ms 冷却吃掉回程 | 归位慢一点就漏 → 横跳 |
| v0.7~v0.9 | 加 `RETURN` 状态：要求手回到出发点并停稳才重新武装 | 稳，但复杂且手感被"必须停一下"绑住 |
| **v0.10** | **只保留冷静期**：触发后一段时间内不识别任何动作，等于把上一轮整段忘掉 | 简单，且方向问题已在坐标系层面解决 |

**关键认识**：当初逼出 `RETURN` 的根因**不是冷却不够长**，而是**方向还判不准**
（左右整体反、斜扫被塞进某个轴）。现在镜像/偏移把坐标系修对了、轴向容差也在了，
`RETURN` 就成了多余的复杂度。

**⚠️ 代价的确切边界**（实测扫描，单位＝画面高度比例）：

| 扫动幅度 | 归位 300ms | 500ms | 600ms | 800ms | 1000ms | 1300ms |
|---|---|---|---|---|---|---|
| ≤ 0.30 | OK | OK | OK | OK | OK | OK |
| 0.35~0.45 | OK | OK | **误触发** | OK | OK | OK |
| 0.50 | OK | **误触发** | **误触发** | **误触发** | OK | OK |
| 0.60 | OK | **误触发** | **误触发** | **误触发** | **误触发** | OK |

规律是两道保护在自动兜底：**归位很快**（整段落在冷静期内）→ 安全；
**归位很慢**（每帧位移掉到死区 0.02 以下）→ 也不累积、安全。
危险的只是**中间那段**（归位约 1~1.6 倍冷静期）**且幅度大**。

**结论与调法**：常规幅度（≤0.30 屏高）在任何归位速度下都安全 —— 正常使用不会遇到。
标定时如果实测幅度偏大（>0.35），App 会直接提示你把冷静期调到 700ms 以上。
这个边界有测试钉住（`test_big_sweep_with_mid_speed_return_is_the_known_weak_spot`），
将来若有人改回保护，测试会立刻失败提醒。

### 7.3 方向"被转了一个直角"（左右扫却触发上下滑）

**现象**：能识别、能触发，但方向整体错了 90°（左右扫 → 上下滑，或反过来）。

**这是坐标系问题，不是算法问题**：判定器的方向角是相对**相机画面**算的，如果画面相对手机
正立方向转了 90°，四个方向就会集体错一个直角。

**修法**：用「方向角整体偏移」把整个方向坐标系转回来——**对纯旋转来说这是精确补偿**，
不是打补丁。两条路：

1. **做一次标定向导**（推荐）：标定会依次让你做四个方向的动作，**不管程序当前把它们认成什么，
   都记录原始角度**，最后算出需要的偏移并写入。现在即使方向全反了标定也能正常工作。
2. **手动旋转修正**：设置里有 `旋转修正：每次 ±90°` 按钮（0 → -90 → +90 → 180 → 0），
   点一下扫两下试，不对再点一次。也可以直接拖「方向角整体偏移」滑块（范围 -180~180）。

> **完全转错的排查顺序**：先点一次 `-90°` 试 → 不行点 `+90°` → 还不行点 `180°`。
> 试出来之后建议再做一次标定，让阈值也按你的实际幅度校准。

> 遗留的小瑕疵：画面被转 90° 时，x 方向的"宽高比折算"用的仍是旋转后的比例，
> 所以**斜着扫**的判定角度会有一点偏差（轴向扫不受影响）。要彻底解决得在送进模型前
> 自己把位图转正——那需要能连真机验证旋转方向，暂时没做。

### 7.4 为什么"调偏移"只能修好一半方向（镜像 ≠ 旋转）

**现象**：把「方向角整体偏移」调到 +90°，上下方向对了，但左右必然反过来；再调偏移去修左右，
上下又错。**怎么调都总有一对方向是反的。**

**根因**：这四个方向之间的关系不是"旋转"，而是"**镜像**"。

把实测角记下来看：向上扫实测 0°、向右扫实测 90°、向下扫实测 180°、向左扫实测 270°，
也就是 `实测角 = 90° − 真实角`。旋转要求 `实测 = 真实 + Δ`（Δ 是常数），而这里 θ 前面的符号是负的。

数学上：**镜像不是旋转，所以不存在任何一个偏移量能同时对齐四个方向。**
把四个方向的"需要的修正量"列出来是 `+90, +90, −90, −90` —— 它们互相抵消，圆均值是 0、残差 180°，
这就是反射的指纹。物理来源也清楚：**前置摄像头画面本身是左右镜像的**，再叠上传感器旋转，
"镜像 ∘ 旋转"就是一个反射。

**修法**：镜像必须做在**坐标层面**（把 x 取反），不能只在最后翻方向标签。
先在坐标上镜像一次，剩下的就变成纯旋转（四个方向的修正量变成一致的 −90°），
一个偏移量就能全部对齐。

标定时程序会**自动判断该不该镜像**：对"镜像/不镜像"两组假设各拟合一次，取残差小的那个。
残差同时告诉你四个方向做得一致不一致（> 35° 就是动作不稳，建议再做一遍）。

> 这两个量是正交的，合起来覆盖方形的全部 8 种对称：
> **镜像（是/否）× 方向角偏移（0/90/180/270）**。
> 有了它们，"朝向"问题就穷尽了，不需要再加别的开关。

### 7.5 三步定位法

App 里（以及悬浮窗上）有三路计数，**它们能直接指出卡在哪一环**：

| 现象 | 结论 | 怎么办 |
|---|---|---|
| **帧**在涨，**回调**一直是 0 | 推理管道断了（图像通道/委托问题） | 点"切换图像通道"，会重启相机 |
| **回调**在涨，**见手**一直是 0 | MediaPipe 没认出你的手 | 手放画面中间、离近一点、开灯；确认是**前置**摄像头对着你 |
| **见手**在涨，但**位移**纹丝不动 | 画面没在更新（相机被别的 App 抢了？） | 关掉相机/微信视频之类的应用，切一下无障碍开关 |
| **位移**在你扫动时会变，但从不触发 | 阈值太大 或 方向角偏移不对 | 调"灵敏度：高"，或重新标定 |
| **并拢**一直 > 1.35 且显示"手指张开" | 门控把所有动作都挡了 | 手指并紧；或把并拢度上限调大（默认 1.35） |
| **角度**方向和你扫的方向对不上 | 支架角度偏了 / 左右镜像反了 | 重新标定；或切换"左右方向反转" |

**一键取证**：点 App 里的「复制诊断信息到剪贴板」，把内容发出来就能定位——
里面包含相机权限、无障碍状态、模型委托（GPU/CPU）、三路计数、当前参数和自诊断提示。

**看日志**（如果有 adb）：

```bat
adb logcat -s SweepDiag SweepService
```

`SweepDiag` 会打印每次触发（方向/位移/角度/并拢）和每 60 帧的计数汇总。
